Por que mudar o destino do COPY

O arquivo já se chamava .template, mas era copiado direto para conf.d/ e nada era substituído. A imagem oficial do Nginx, ao subir, pega tudo que está em /etc/nginx/templates/*.template, troca as ${VARIAVEIS} pelos valores do ambiente (envsubst) e grava o resultado em /etc/nginx/conf.d/.

E o $uri, $host...?

O envsubst da imagem só troca variáveis que existem no ambiente. As variáveis do próprio Nginx ($uri, $host, $remote_addr) continuam intactas. O container já recebia o .env via env_file, então o NGINX_PORT chega sem mais nada.

Atualize seu .env:

quem já tem .env precisa adicionar NGINX_PORT=80. Sem ela, o compose avisa variável vazia e o mapeamento de porta quebra. O NGNIX_WEB_PORT (com o erro de digitação) foi mantido para não quebrar os .env existentes.

Testado:

docker compose config ok; docker compose build nginx-container ok; container com o template em /etc/nginx/templates/ → nginx -t ok e conf.d/default.conf gerado com listen 80; e $uri/$host preservados.

Por que ./src:/app

É o padrão do projeto de Desenvolvimento Web (.:/app). Com tudo na raiz, montar pasta por pasta viraria uma lista enorme. Por cima do src/ montado ficam o nodemodules-volume (em /app/node_modules) e o public-volume (em /app/public), que o compilador do Vite escreve e o Nginx serve.

Por que o nodemon.json

Com o src/ inteiro montado, o nodemon passou a enxergar o public/, onde o Vite escreve .js a cada build. Resultado: 13 reinícios em 10 segundos depois de salvar um .ts. Ignorando public/, resources/, storage/ e logs/, voltou a 0, e uma mudança em routes/ continua reiniciando.

Sem bloco ports

Nenhuma porta da máquina aponta para o Elasticsearch. Só quem está na app-network chega nele, pelo endereço elasticsearch_host:9200: o servidor web (busca), o command (criar índice, carga inicial) e, depois, o worker (alimenta). O navegador nunca fala direto com o Elastic: toda busca passa pela API.

As três variáveis

Como testar em aula:

O Vite gera nomes com hash (src/app.aQR1sM3P.js). A View não tem como adivinhar. O manifest.json (ligado desde a Aula 05) tem o mapa fonte → compilado, e o helper transforma isso em tags.

Arquivo novo: utils/vite.js

src/utils/vite.js
+ import fs from 'node:fs';
+ import path from 'node:path';
+ import CONSTANTS from '../bootstrap/config.js';
+
+ /**
+ * Ponte entre a View (servidor) e o Vite (frontend compilado).
+ *
+ * O Vite gera os arquivos com hash no nome (ex.: src/login.COZhj-27.js), então
+ * a View não sabe o nome final. Com build.manifest: true (vite.config.js), o
+ * Vite grava em public/.vite/manifest.json o mapa "arquivo fonte -> compilado".
+ *
+ * Uso na view: <%- vite(["css/app.css", "js/app.ts"]) %>
+ * Devolve as tags <link> e <script> já com os nomes compilados.
+ */
+ export default function vite(entries) {
+ // Lido a cada chamada: o "vite build --watch" reescreve o manifest a cada mudança
+ const manifestPath = path.join(CONSTANTS.DIR, 'public', '.vite', 'manifest.json');
+ const manifest = JSON.parse(fs.readFileSync(manifestPath, 'utf-8'));
+
+ const styles = new Set();
+ const scripts = [];
+
+ for (const entry of entries) {
+ const chunk = manifest[entry];
+
+ if (!chunk) {
+ throw new Error(`Entrada "${entry}" não existe no manifest do Vite (faltou no rollupOptions.input?)`);
+ }
+
+ collectCss(manifest, entry, styles);
+
+ if (chunk.file.endsWith('.css')) {
+ styles.add(chunk.file);
+ continue;
+ }
+
+ scripts.push(chunk.file);
+ }
+
+ const tags = [];
+
+ for (const file of styles) {
+ tags.push(`<link rel="stylesheet" href="/${file}">`);
+ }
+
+ for (const file of scripts) {
+ tags.push(`<script type="module" src="/${file}"></script>`);
+ }
+
+ return tags.join('\n');
+ }
+
+ /**
+ * Um chunk JS pode importar outros chunks que têm CSS próprio:
+ * percorre os imports para não esquecer nenhuma folha de estilo.
+ */
+ function collectCss(manifest, key, styles) {
+ const chunk = manifest[key];
+
+ if (!chunk) {
+ return;
+ }
+
+ for (const file of chunk.css ?? []) {
+ styles.add(file);
+ }
+
+ for (const imported of chunk.imports ?? []) {
+ collectCss(manifest, imported, styles);
+ }
+ }

src/app/Services/UserElasticService.js (acrescentado antes do export default)
+ /** Campos de texto: buscados como "contém" (LIKE '%valor%') */
+ const TEXT_FIELDS = ['name', 'email', 'job_title', 'bio', 'city', 'state'];
+
+ /** Campos de data: buscados por intervalo { gte, lte } */
+ const DATE_FIELDS = ['birth_date', 'created_at'];
+
+ /** Campos booleanos: buscados pelo valor exato */
+ const BOOLEAN_FIELDS = ['is_active'];
+
+ /** * e ? são curingas do wildcard: o que o usuário digitou é escapado para virar texto */
+ function escapeWildcard(value) {
+ return String(value).replace(/[\\*?]/g, (char) => `\\${char}`);
+ }
+
+ /**
+ * Monta a query do Elastic a partir dos filtros do body.
+ * Todos os filtros valem juntos (AND), dentro de um bool.filter.
+ * Lança erro se vier um campo que não existe no índice.
+ */
+ function buildQuery(filters) {
+ const filter = [];
+
+ for (const [field, value] of Object.entries(filters)) {
+ if (value === undefined || value === null || value === '') {
+ continue;
+ }
+
+ if (TEXT_FIELDS.includes(field)) {
+ // LIKE '%valor%': *valor* no subcampo .keyword (texto inteiro), sem diferenciar maiúscula
+ filter.push({
+ wildcard: {
+ [`${field}.keyword`]: {
+ value: `*${escapeWildcard(value)}*`,
+ case_insensitive: true
+ }
+ }
+ });
+ continue;
+ }
+
+ if (BOOLEAN_FIELDS.includes(field)) {
+ filter.push({ term: { [field]: value === true || value === 'true' } });
+ continue;
+ }
+
+ if (DATE_FIELDS.includes(field)) {
+ // { "gte": "1990-01-01", "lte": "1999-12-31" }: só as pontas que vierem
+ filter.push({ range: { [field]: { gte: value.gte, lte: value.lte } } });
+ continue;
+ }
+
+ throw new Error(`Campo de busca inválido: ${field}`);
+ }
+
+ return { bool: { filter: filter } };
+ }
+
+ /**
+ * Etapa 1 da busca: o Elastic resolve os filtros e devolve SÓ os ids (_source: false).
+ * Os dados completos vêm depois do Postgres, pelo WHERE IN (fonte da verdade).
+ */
+ async function searchIds(filters, { page, limit }) {

+ _source: false,
+ from: (page - 1) * limit,
+ size: limit,
+ track_total_hits: true,
+ sort: [{ created_at: 'desc' }],
+ query: buildQuery(filters)
+ });
+
+ return {
+ total: data.hits.total.value,
+ ids: data.hits.hits.map((hit) => Number(hit._id))
+ };
+ }

Quem aparece x o que aparece

O Elastic decide quem aparece e em que ordem (_source: false: só ids, já com from/size da página). O Postgres decide o que aparece: os dados vêm da fonte da verdade. Um usuário excluído há pouco, que o job ainda não tirou do índice, não volta no WHERE IN e some da resposta.

LIKE '%x%' no Elastic

wildcard com *valor* no subcampo .keyword (o valor inteiro, sem quebrar em palavras) e case_insensitive: true. O escapeWildcard transforma * e ? digitados pelo usuário em texto, para não virarem curinga.

Reordenar

O WHERE IN não garante ordem nenhuma. O Map por id remonta a lista na ordem que o Elastic devolveu.

Filtros em bool.filter

Todos os filtros entram no bool.filter: valem juntos (E), sem cálculo de relevância. Campo fora das listas → buildQuery lança erro → 400. Sem else: continue em cada tipo de campo.

Para a busca achar alguém:

o índice users precisa existir e estar populado: o seed faz a carga inicial (etapa 11) e o worker mantém o índice em dia a cada action (etapa 10).
