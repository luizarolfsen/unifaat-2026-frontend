Por que essa organização (e não tudo num arquivo só)

Separar Controllers (o que cada rota faz), Models (o que é um Usuário/Tarefa no banco), Middlewares (o que roda antes de toda rota, tipo autenticação) e routes (o "mapa" de URLs) é o padrão MVC simplificado. Cada arquivo tem uma responsabilidade só — quando algo quebra, o nome da pasta já diz onde procurar.

Dois entrypoints, dois propósitos

_web.js sobe o servidor (fica rodando, escutando requisições). _command.js roda um comando e termina (migrate, seed). Misturar os dois num arquivo só faria o "rodar uma migration" depender de subir o servidor inteiro à toa.

Etapa 2

Instalando o JWT: jsonwebtoken + bcrypt

Duas libs via npm — uma pra gerar/validar o token, outra pra nunca guardar senha em texto puro.

terminal — dentro de src/
$ npm install jsonwebtoken bcrypt
src/package.json
+ "bcrypt": "^6.0.0",
+ "jsonwebtoken": "^9.0.3",

Onde o JWT é gerado

backend/app/Http/Controllers/LoginController.js
const isPasswordValid = await bcrypt.compare(password, user.password);
if (!isPasswordValid) { return response.status(401)...; }
+ const token = jwt.sign(
+ { id: user.id },
+ process.env.JWT_SECRET,
+ { expiresIn: "10m" }
+ );
+
+ response.cookie("auth_token", token, {
+ httpOnly: true,
+ sameSite: "lax",
+ maxAge: 10 * 60 * 1000
+ });

Onde o JWT é validado

backend/app/Http/Middlewares/AuthMiddleware.js e AuthTokenMiddleware.js
const decoded = jwt.verify(token, process.env.JWT_SECRET);
request.user = decoded; // fica disponível pros controllers
next();

Por que bcrypt e não guardar a senha direto

bcrypt.compare nunca "descriptografa" a senha salva — ele recria o hash da senha digitada e compara os hashes. Isso significa que, mesmo se o banco vazar, ninguém recupera a senha original a partir do que está guardado.

Por que o cookie é httpOnly

Um cookie httpOnly não pode ser lido por JavaScript no navegador (document.cookie não mostra ele). Isso bloqueia um ataque comum: um script malicioso injetado na página tentando roubar o token.

Dois middlewares de JWT, um motivo

AuthMiddleware.js só aceita o token no header Authorization: Bearer (útil pra testar a API direto, ex: Postman/Swagger). AuthTokenMiddleware.js aceita cookie OU header — é o que o frontend usa de verdade, já que o navegador manda o cookie sozinho em toda requisição.

Etapa 3

Como organizei o login no frontend

Três arquivos, cada um com uma responsabilidade — mas montando a tela na mão, no JavaScript.

js/pages/login.js // decide: já autenticado? manda pra /tasks. senão, chama os dois abaixo js/render/loginRender.js // cria o <form> inteiro via document.createElement(...) js/listeners/loginListeners.js // escuta o submit, chama a API, trata erro
js/render/loginRender.js — como o form nasce
const formElement = document.createElement("form");
const emailInputElement = document.createElement("input");
emailInputElement.type = "email";
emailInputElement.classList.add("form-control");
...
formElement.append(titleElement, emailLabelElement, emailInputElement, ...);
container.append(formElement);
Isso é um jeito ruim de fazer — e de propósito, por enquanto.

Montar uma tela inteira chamando document.createElement várias vezes é verboso, difícil de ler e fácil de errar (esquecer um .append, uma classe, um id). O jeito certo seria escrever o HTML como template e só plugar os dados nele — isso é o conceito de view. Ainda não vimos views nessa disciplina, então por ora o login é montado assim, "na unha", só pra já ter uma tela funcionando. Isso muda quando chegarmos nesse assunto.

Por que separar render / listeners / pages mesmo sendo "temporário"

Mesmo sem view "de verdade" ainda, já vale separar o que desenha (render) de o que reage a evento (listeners) de o que orquestra a página (pages). Quando views entrarem, só o render muda — listeners e pages continuam do mesmo jeito.
