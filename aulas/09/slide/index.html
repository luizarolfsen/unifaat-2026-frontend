Variáveis, const derivados, funções internas e o JSX: tudo é recriado a cada renderização. Só o estado (e a ref) vive fora da função.

Observação: o count é uma foto nova a cada execução (frame novo). A ref é um só objeto: o endereço 0x3C não muda, só o conteúdo.

  1. 1. Primeira renderização: useRef(0) cria { current: 0 } no heap; a variável guarda o endereço.
  2. 2. clicksRef.current += 1 altera o objeto no lugar. Nenhuma renderização: o count continua 0 na tela.
  3. 3. Agora o estado muda: o componente roda de novo (frame novo, count = 1) e a ref persiste: mesmo 0x3C, current ainda 1.
  4. 4. Outra mudança na ref: current vai a 2, e de novo a tela não se mexe.
  5. 5. A próxima renderização (por causa do estado) encontra a ref exatamente como você a deixou. Só muda se você modificar.

O usuário precisa ver a mudança? Estado. Só o código precisa lembrar? Ref. E nunca leia nem escreva ref.current durante a renderização: só em handlers e efeitos.

Ref para o HTML e para componentes

Criar. O generic diz qual elemento vai morar ali. Começa em null: antes de montar não há elemento.

Ligar. A prop ref entrega o elemento ao React, que o coloca em current depois de montar (e volta a null ao desmontar).

Acionar. Com o elemento em mãos, chamamos os métodos nativos do HTML: focus(), click() de um input file escondido, requestSubmit(). O ?. cobre o null.

Componente. No React 19, ref é um parâmetro comum: o filho decide a quem entregar, e o pai passa a controlar aquele elemento. Com useImperativeHandle o filho expõe só os métodos que quer.

Efeito: a ação da transição de estados

ideia

Depois que o estado é atualizado (e a tela já foi desenhada), executa-se o efeito dessa mudança: buscar na API, assinar um evento, mexer no título da aba.

O componente só calcula tela. O efeito é o lugar do que acontece fora dela.

Renderiza, desenha a tela, e só então o efeito

1O evento chama setEstado: o React agenda uma renderização
2A função do componente roda inteira e devolve o JSX
3O React atualiza o DOM e o navegador pinta a tela
4Só então rodam os efeitos cujas dependências mudaram (a limpeza do anterior vem antes)
5O efeito chama setEstado com a resposta da API: volta ao passo 1
useEffect(() => {
  // 1 · o efeito: DEPOIS da tela
  return () => {
    // 2 · a limpeza
  }
}, [deps]) // 3 · quando roda de novo
  1. Passo 1. Tudo começa com uma mudança de estado, por clique ou por resposta de API.
  2. Passo 2. A renderização é só cálculo: a função roda e descreve a tela.
  3. Passo 3. O usuário já enxerga a tela (por exemplo, "Carregando...") antes de o efeito existir.
  4. Passo 4. O efeito é a ação da transição: chamada ao backend, assinatura, timer.
  5. Passo 5. A resposta vira estado de novo, e o ciclo completo recomeça.

AbortController: cancela a requisição velha

1Clica em Ana: o efeito dispara GET /users/7/tasks com o signal do controller dela
2Antes da resposta, clica em Bruno: a dependência user.id muda
3ERRADO, sem abort: a resposta de Ana chega depois e sobrescreve a tela de Bruno
4Com abort: a limpeza chama controller.abort(); o GET de Ana rejeita com CanceledError e o isCancel ignora
5Só a resposta de Bruno vira estado: a tela e o nome combinam
# ① cria o controle (API nativa do navegador)
const controller = new AbortController()
# ② entrega o signal à requisição
get(url, { signal: controller.signal })
# ③ na limpeza do efeito, cancela
return () => controller.abort()
# É do navegador, não do React nem do Axios.
# O abort só faz o cliente parar de esperar:
# o que o servidor já processou não desfaz.
  1. Passo 1. O efeito cria um AbortController, passa o signal dele ao Axios e devolve a limpeza.
  2. Passo 2. A resposta de Ana ainda não chegou e o usuário escolhe outro: é a condição de corrida.
  3. Passo 3. Sem cancelar, quem responde por último vence: a rede não garante a ordem das respostas.
  4. Passo 4. A limpeza roda antes do próximo efeito: abort() cancela só o GET de Ana (o de Bruno tem outro controller).
  5. Passo 5. O cancelamento não é falha de verdade: por isso o isCancel(err) sai sem mostrar erro.

O hook feito por nós: useAxios e a tela dele

export function useAxios<T>(url, onEvent?) {
  const [data, setData] = useState<T | null>(null)
  const [error, setError] = useState("")

  const onEventRef = useRef(onEvent) // ref: fora das deps
  useEffect(() => { onEventRef.current = onEvent })
  useEffect(() => {
    const controller = new AbortController()
    const request = { isPending: true }
    async function load() { /* GET + estados */ }
    load() // o efeito em si não é async
    return () => {
      if (!request.isPending) return // já chegou
      controller.abort()
    }
  }, [url, attempt]) // só primitivos
  return { data, error, isLoading, refetch }
}

  1. 1. UserTasks monta. O hook cria três estados, que pertencem ao componente: isLoading começa verdadeiro e a tela já diz "Carregando".
  2. 2. Depois da tela, o efeito do hook dispara o GET. O componente não escreveu um useEffect.
  3. 3. A resposta chega: o hook chama setData e setIsLoading(false). Quem renderiza de novo é o UserTasks (o pai não).
  4. 4. Outro usuário (key muda): o componente desmonta, a limpeza cancela a requisição se ela ainda estiver no ar (isPending) e o novo nasce com os estados do zero.

Cada chamada ao hook tem os seus estados: o hook reaproveita lógica, não dados.
