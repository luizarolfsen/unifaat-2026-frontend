1
Etapa 1

Observação: o package.json real mora em src/

Criamos aliases no package.json da raiz do repo pra não precisar lembrar de entrar em src/ toda hora.

./ // raiz do repositório (aulas/, docker/, docker-compose.yml...) ├── package.json ← NOVO: só aliases, sem dependências próprias └── src/ └── package.json // o package.json "de verdade": deps do backend + frontend
./package.json (raiz)
{
"scripts": {
"web": "cd src && node _web.js",
"dev": "cd src && npm run dev",
"migrate": "cd src && node _command.js migrate",
"seed": "cd src && node _command.js seed",
"i": "npm --prefix src install",
+ "vite:dev": "cd src && npx vite",
+ "vite:build": "cd src && npx vite build",
+ "vite:watch": "cd src && npx vite build --watch",
+ "docker:build":"docker compose build",
+ "docker:up": "docker compose up -d",
+ "docker:down": "docker compose down"
}
}

Por que dois package.json

O de src/ é o real: lista express, axios, bootstrap, vite, typescript etc — é onde npm install baixa coisa de verdade. O da raiz não tem dependencies nenhuma: existe só pra guardar atalhos (aliases), porque rodar comandos direto da raiz do projeto (onde também está o docker-compose.yml) é mais natural do que ficar entrando/saindo de src/.

"cd src &&" em vez de "--prefix"

A opção npm --prefix src exec vite build parece equivalente, mas não muda o diretório de trabalho do comando — só troca de onde o npm busca o binário. Como o vite.config.js usa caminhos relativos (root: 'frontend/resources'), rodar com o cwd errado quebra a resolução do index.html. cd src && npx vite build resolve isso rodando o comando de dentro da pasta certa.

Testado:

npm run vite:build (da raiz) → build de produção completo. npm run docker:build -- nodevitecompiler-container → imagem buildada. Os aliases antigos (web, dev, migrate, seed, i) continuam intactos.

Etapa 2

Criando o diretório resources/

Separar código-fonte (o que escrevemos) do código de saída (o que o navegador recebe).

frontend/ ├── public/ // antes: tinha TUDO aqui │ ├── index.html, login.html, tasks.html │ ├── css/app.css // ← saiu daqui │ └── js/... // ← saiu daqui ⬇ frontend/ ├── public/ // depois: só o que o Vite GERA └── resources/ ← NOVO (fonte) ├── css/app.css └── js/ (api/, listeners/, pages/, render/, utils/)

Por que

O Vite precisa de uma pasta de origem diferente da pasta de destino. Sem isso, não dá pra saber o que é escrito à mão e o que é gerado automaticamente.

Etapa 3

Migrando todo o JavaScript para TypeScript

24 arquivos .js → .ts, com tipos e um arquivo central de generics para as respostas de API.

Arquivo novo: types/api.ts

resources/js/types/api.ts
+ export interface User { id: number; name: string; email: string; }
+ export interface Task { id: number; name: string; is_done: boolean; id_user: number; }
+ // Generic: T é o tipo do item da lista (Task, User, ...)
+ export interface PaginatedResponse<T> {
+ data: T[]; page: number; limit: number; total: number;
+ }
+ export type ValidationResult =
+ | { valid: true; data: User }
+ | { valid: false };

Antes / depois de uma API típica

resources/js/api/tasksListApi.ts
- export async function tasksListApi(idUser, { page = 1, limit = 10 } = {}) {
- const { data } = await clientApi.get(`/users/${idUser}/tasks`, { params: { page, limit } });
- return data;
- }
+ export async function tasksListApi(
+ idUser: number,
+ { page = 1, limit = 10 }: PaginationParams = {}
+ ): Promise<PaginatedResponse<Task>> {
+ const { data } = await clientApi.get<PaginatedResponse<Task>>(`/users/${idUser}/tasks`, {
+ params: { page, limit },
+ });
+ return data;
+ }

Por que um generic e não um tipo fixo

PaginatedResponse<T> descreve o "formato" comum de qualquer lista paginada do backend (page, limit, total, data). Em vez de criar TaskListResponse, UserListResponse etc. repetidos, escrevemos a forma uma vez e reaproveitamos trocando só o T.

Generic direto no Axios

clientApi.get<PaginatedResponse<Task>>(...) diz ao TypeScript: "o .data dessa resposta é desse tipo". A partir daí, autocompletar e checagem de tipos funcionam em toda a cadeia — sem precisar de type assertion manual.

Cleanup no caminho:

4 arquivos (createButtonClickHandler.js, deleteButtonClickHandler.js, userRender.js, paginationRender.js) importavam um listUserRender.js que não existe no projeto e não eram usados por nenhuma página. Código morto e já quebrado antes desta aula — removidos em vez de convertidos.

Etapa 4

Configurando o vite.config.js como entry point

De "servidor com HMR" pra "pré-compilador profissional": resources/ → public/.

src/vite.config.js
- root: (IS_DOCKER == "true") ? 'resources' : 'frontend/public',
+ root: 'frontend/resources',
server: { open: ..., hmr: true, host: true, port: (IS_DOCKER ? 5172 : 5173) },
+ resolve: { alias: { '@fa': '.../@fortawesome/fontawesome-free' } },
+ build: {
+ outDir: '../public', // frontend/resources/../public = frontend/public
+ emptyOutDir: true,
+ manifest: true,
+ rollupOptions: { input: ["index.html", "login.html", "tasks.html"] }
+ }

Por que tirei a bifurcação "docker vs local" do root

A config antiga tinha dois roots diferentes (um pra Docker, outro local) porque resources/ ainda não existia — o modo local caía direto em frontend/public. Agora que resources/ é a única fonte de verdade, os dois ambientes devem compilar o mesmo código-fonte. Só porta e abrir navegador automaticamente continuam diferentes por ambiente — isso é o "hmr" que pedimos pra preservar.

index.html, login.html e tasks.html também se mudaram

O Vite entra em um projeto pelos arquivos .html configurados em root. Como o root virou frontend/resources, os três HTMLs (e a pasta img/, 404.html, example.json como resources/public/) precisaram ir junto — senão o Vite não encontraria nada pra compilar.

Testado:

tsc --noEmit → 0 erros de tipo. vite build → build de produção gerando frontend/public/ do zero (78 módulos, HTML + JS + CSS com hash). frontend/public/ agora é 100% gerado, então entrou no .gitignore — como um dist/.

Etapa 5

Bootstrap, Axios e FontAwesome: do CDN pro npm

De tags <script>/<link> apontando pra internet, pra dependências instaladas e compiladas pelo Vite — incluindo os ícones.

resources/login.html · resources/tasks.html
- <link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/.../bootstrap.min.css">
- <script src="https://cdn.jsdelivr.net/npm/axios@1.7.9/dist/axios.min.js"></script>
- <script src="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/.../bootstrap.bundle.min.js"></script>
+ <link rel="stylesheet" href="./css/app.css">
+ <script type="module" src="./js/app.ts"></script>
resources/js/app.ts · resources/css/app.css
+ import "bootstrap/dist/js/bootstrap.bundle.min.js";
+ import axios from "axios";
+ @import "bootstrap/dist/css/bootstrap.min.css"; /* topo do app.css */
+ @import "@fortawesome/fontawesome-free/css/all.min.css";

FontAwesome entrou pelo mesmo caminho

terminal — dentro de src/
$ npm install @fortawesome/fontawesome-free

Por que sair do CDN

No CDN, a versão fica escrita na URL do HTML — fácil de esquecer, difícil de auditar. Pelo npm install, a versão fica no package.json, versionada junto do resto do projeto, e o Vite baixa uma vez só (sem requisição externa toda vez que a página carrega).

Por que centralizar em app.ts

Bootstrap, Axios e FontAwesome não são código nosso — são "vendor". Colocar os imports num arquivo só (app.ts/app.css, carregado em toda página) deixa claro o que é dependência externa vs. o que é lógica da aplicação (que fica em pages/, api/, etc).

O alias @fa da Etapa 3 finalmente ganhou uso

O vite.config.js já tinha um alias '@fa' apontando pra node_modules/@fortawesome/fontawesome-free desde que criamos o entry point — só não existia o pacote instalado ainda. Agora ele resolve de verdade.

Testado:

Build gerou checkAuthentication.*.css (agora 316KB → 54KB gzip, Bootstrap + FontAwesome juntos) e 4 arquivos de fonte (fa-solid, fa-regular, fa-brands, fa-v4compatibility, todos .woff2 com hash). Nenhuma tag de CDN restante em nenhum .html do app.

Etapa 6

Container Docker do pré-compilador (vite build --watch)

Um 3º container além do Nginx e do Node web: fica só compilando resources/ → public/ em background, sem servir nada.

docker/ ├── node-web/ // Express (API) ├── node-command/ // comandos avulsos (migration, seed...) ├── node-vite-hmr/ // dev server com HMR (porta 5172) └── node24-vite-compiler/ ← NOVO ├── Dockerfile └── vite.config.js // root:'resources' → outDir:'../public'

Dockerfile

docker/node24-vite-compiler/Dockerfile
FROM node:24
WORKDIR /app
COPY src/package*.json ./
COPY src/frontend/resources/ ./resources/
COPY docker/node24-vite-compiler/vite.config.js ./
RUN npm install && npm install -g vite
+ ENTRYPOINT ["vite", "build", "--watch"]

docker-compose.yml — 3 mudanças

docker-compose.yml
+ nodevitecompiler-container:
+ volumes:
+ - public-volume:/app/public
+ - ./src/frontend/resources:/app/resources
+ - nodemodules-volume:/app/node_modules
+ environment: [IS_CONTAINER=TRUE]
- nodeweb-container: volumes: ./src/frontend/public:/app/frontend/public
+ nodeweb-container: volumes: public-volume:/app/frontend/public
- nginx-container: volumes: ./src/frontend/public:/var/www
+ nginx-container: volumes: public-volume:/var/www

Por que um vite.config.js separado pra esse container

O vite.config.js principal (usado no HMR local) tem root: 'frontend/resources', porque lá backend e frontend dividem o mesmo src/. Dentro desse container, porém, o Dockerfile copia resources/ direto pra /app/resources — sem o prefixo frontend/. Por isso o config daqui usa root: 'resources', batendo com os binds /app/resources e /app/public.

Por que public virou um volume Docker (não mais bind do host)

Como public/ agora é 100% gerado (e já está no .gitignore), não precisa mais existir como pasta real no host. Um named volume (public-volume) guarda esse output só dentro do Docker, e os 3 containers que precisam dele (compilador que escreve, Nginx e Node web que leem) montam o mesmo volume — sem duplicar arquivo em disco.

Por que node_modules continua compartilhado

Os outros 3 containers Node (web, command, vite-hmr) já dividem nodemodules-volume porque todos instalam a partir do mesmo src/package.json (backend e frontend juntos). O compilador entra nesse mesmo esquema — não precisa de um volume próprio.

Testado:

docker compose build nodevitecompiler-container → build limpo. docker compose up -d → log mostrou watching for file changes..., build inicial rodou (78 módulos) e escreveu em /app/public dentro do volume. Container parado depois do teste.

Etapa 7

Os HTMLs apontam pra .ts direto — o Vite resolve isso no build

O navegador nunca vê a palavra .ts. Quem escreve .ts nos scripts somos nós; quem entrega .js pro navegador é o pré-compilador.

Fonte: resources/login.html

resources/login.html (o que a gente escreve)
<link rel="icon" type="image/png" href="./img/favicon.ico">
<link rel="stylesheet" href="./css/app.css">
+ <script type="module" src="./js/app.ts"></script>
+ <script type="module" src="./js/pages/login.ts"></script>

Saída: public/login.html (depois do build)

public/login.html (o que o navegador recebe)
<link rel="icon" type="image/png" href="./img/favicon.ico">
+ <script type="module" crossorigin src="/src/login.CaImtk-5.js"></script>
+ <link rel="modulepreload" crossorigin href="/src/checkAuthentication.DoW8m8Fp.js">
+ <link rel="stylesheet" crossorigin href="/src/checkAuthentication.BqMNcqKe.css">

Por que dá pra escrever ".ts" dentro de um <script>

O navegador não entende .ts (ver Etapa 2 e a Seção 2 do README da aula). O truque é que quem serve esse HTML nunca é o arquivo cru — é sempre o Vite: no dev (HMR) ele intercepta a requisição e compila na hora; no build, ele reescreve o próprio HTML, trocando cada src="./js/....ts" pelo caminho do bundle .js final, com hash.

De onde vem o hash no nome do arquivo

login.CaImtk-5.js — o hash muda toda vez que o conteúdo muda. Isso permite cache "forte" no navegador (o arquivo pode ficar guardado por anos), porque se o código mudar, o nome do arquivo muda junto e o navegador é obrigado a buscar de novo.

modulepreload e o CSS "vazando" pro JS

O checkAuthentication.*.css e o checkAuthentication.*.js aparecem porque app.ts (Bootstrap+Axios) e várias funções de API são código compartilhado entre login.ts e tasks.ts — o Vite extrai isso num "chunk" comum em vez de duplicar em cada página.

Não é só .ts — as imagens também passam pelo pré-compilador

favicon.ico e squirtle.png ficam em resources/public/img/ (a pasta especial que o Vite copia sem processar) e saem em public/img/ depois do build, junto com o .vite/manifest.json. A referência href="./img/favicon.ico" não muda de um lado pro outro — o Vite só garante que o arquivo exista no destino certo.

Testado:

Rodei vite build de novo e li o public/login.html gerado: confirma que o ./js/app.ts e o ./js/pages/login.ts viraram um único <script> apontando pro bundle final — nenhuma referência a .ts sobra no HTML entregue ao navegador. public/img/favicon.ico e public/img/squirtle.png saíram junto no mesmo build.

Etapa 8

API Contextual de Tasks — a API antiga continua viva

Um diretório novo de controllers, TaskViewContextApi/, do lado do TaskApi/ já existente — sem apagar nada.

backend/app/Http/Controllers/ ├── TaskApi/ // intacta — idUser vem da URL │ ├── ListTaskController.js │ ├── GetTaskController.js │ ├── CreateTaskController.js │ ├── UpdateTaskController.js │ └── DeleteTaskController.js │ └── TaskViewContextApi/ ← NOVO — idUser vem do JWT ├── ListTaskController.js ├── GetTaskController.js ├── CreateTaskController.js ├── UpdateTaskController.js └── DeleteTaskController.js

+ export default async function GetTaskController(request, response) {

Rotas novas em router.js

backend/routes/router.js
router.use("/users/:idUser/tasks", taskRouter); // continua existindo
+ router.use("/me/tasks", AuthTokenMiddleware, taskContextRouter);

Por que não apagar a API antiga

/users/:idUser/tasks ainda faz sentido pra um admin listar tarefas de qualquer usuário (uso que exige saber o ID de outra pessoa). /me/tasks é pro caso comum: o próprio usuário logado mexendo nas próprias tarefas. São dois casos de uso diferentes, não uma versão "certa" substituindo a "errada".

Onde entra o AuthTokenMiddleware

Ele roda antes de qualquer controller de /me/tasks, decodifica o JWT (do cookie ou do header) e guarda o resultado em request.user. Se o token não existir ou for inválido, a requisição nem chega no controller — já leva 401.

O que sai do controller

Como o idUser não vem mais da URL, o bloco "verifica se o usuário existe" (que existia pra prevenir um idUser forjado) deixa de fazer sentido — o middleware já garantiu que o token é válido. O controller fica mais curto e só cuida da regra de negócio da task.

Testado:

node --check em todos os arquivos novos → sem erro de sintaxe. node _web.js subiu sem quebrar no import/wiring das novas rotas.
